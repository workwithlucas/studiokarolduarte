## 1. Backlog replay (03/10 and 04/10 answered on 05/10 ~15:41)

**PROVEN (code).** Code path, in order:

1. While `agent_mode = 'off'`, `wa-webhook` -> `handleReceived` (`_shared/webhook.ts:50-61`) still ingests the inbound via `agent_ingest_inbound` (migration `20261002120000_agent.sql`). That sets `wa_conversations.pending_since` and `last_inbound_at`, then returns `{action:'stopped'}` at `webhook.ts:61`. **`pending_since` is never cleared and the message is kept as pending indefinitely.**
2. pg_cron job `wa-sweep` runs every minute (`20261002120100_agent_cron.sql`). `_cron_wa_sweep()` calls the `wa-sweep` function whenever any conversation has `pending_since` older than 60 s.
3. `runSweep` (`_shared/sweep.ts:23-39`) returns early only while mode is `off`. The moment the panel set mode to `test`/`live`, it selected every conversation with `pending_since is not null`, `mode='agent'`, `failed_runs < 3`, with **no limit on message age**, and called `invokeAgentRun` for each (up to 20 in parallel).
4. `runClaimed` (`_shared/agent.ts:51-166`) has no age gate and no "already answered" gate. It builds history, calls the model and sends.

So the replay path is: **panel mode switch -> pg_cron `wa-sweep` (<= 60 s later) -> `runSweep` -> `agent-run` -> `runClaimed` -> Z-API `sendText`.** The ~15:41 time is the moment the mode was switched plus up to a minute.

Ruled out: webhook redelivery. A redelivered `messageId` hits `on conflict (external_id) do nothing` and returns `duplicate` (`webhook.ts:55`), no run. Panel action: the panel only changes settings (`rpc_agent_set_settings`) and "Devolver à Thaís" (`rpc_agent_return_conversation`); neither sends.

Secondary contributor: `rpc_agent_return_conversation` and the human-return sweep do not look at message age either.

## 2. Human reply ignored

**PROVEN (code).** Three causes:

- `webhook.ts:42`: for a `fromMe` event, `if (!modeAllows(settings, ev.phone)) return ignored 'mode'` runs **before anything is stored**. While mode is `off` (or `test` for a non-listed number), staff messages typed on the phone are dropped entirely: not stored, no `agent_mark_human`, no takeover window. The flag/window is only set in an active mode.
- `webhook.ts:41`: `fromApi === true` is ignored. Anything another sender sent through the API (old agent) is invisible to this system.
- `runClaimed` only checks `conv.mode === 'human'` at the start (`agent.ts:57`). It never checks whether an outbound exists after the inbound. A staff reply that arrives while the model is generating (up to 60 s budget) is not seen: the only re-check before send is "newer inbound" (`agent.ts:136-137`).

So: staff answered from the phone while mode was off -> nothing stored -> on mode switch the sweep still saw `pending_since` and answered the client again.

## 3. Identity: Graziella Matteussi, Mayara Fernandes, Lizandra (Esmalte em Gel), Rafaela Mafezzoli

**Mechanism PROVEN (code); per-client rows NEEDS PROD DATA.**

- `rpc_find_client_by_phone` (`20260929120200_rpc_catalog_clients.sql:168`) matches `clients.phone_e164 = normalize_phone(p_phone)`: **exact string equality**.
- `normalize_phone` keeps 12-13 digits starting with 55 as is. A client stored by staff as `47 9625-2877` becomes `554796252877` (no 9th digit). The inbound from Z-API arrives as `5547996252877`. Different strings, **no match**, so `lookup_client` returns "Nenhum cadastro: pergunte o nome" and the agent asks the name of a client who already exists.
- `register_client` -> `rpc_upsert_client` (`20261001120000_crm_packages.sql:156`) only merges when the phone is equal and name similarity >= 0.82. Otherwise it **inserts a duplicate** client with the 13-digit phone. The staff-booked appointment stays under the old client, so the agent also does not see the existing appointment.
- A client who "succeeded" is one whose stored phone happens to be in the same 13-digit form as the inbound.
- `lookup_client` is the only identity path; `appointments` found by phone do not exist.

Per-client table to fill from prod (query 8.3): raw `clients.phone_e164`, inbound number (`wa_conversations.phone_e164`), appointments and owning client, lookup result. Prediction from the code: any of the four whose staff-entered phone lacks the 9th digit (or has a different DDD format) failed; any with a 13-digit stored phone succeeded.

## 4. Kill switch

**PROVEN (code) paths that can send after the panel is set to off:**

| # | Path | Why it survives off |
|---|---|---|

| b | Sweep fan-out | `runSweep` starts up to 20 `agent-run`s in parallel; each already passed its start-of-run check. |
| c | Webhook debounce | `webhook.ts:68-70` sleeps `debounce_seconds` then `invokeRun`; the run re-checks mode at its start only (so this path is closed after the sleep, but the in-flight generation after it is path a). |
| d | `send-confirmations` / `notify-reschedule` | Check mode once at their start (`confirmations.ts:33`, `reschedule.ts:36`); a batch already running keeps sending (up to 110 s budget). |
| e | Another sender | See below. |

**Comparison with this system's send log: NEEDS PROD DATA** (query 8.4). Every system send is stored in `wa_messages` (direction `out`, `external_id` = Z-API message id). Any outbound seen by Z-API / the phone since 15:30 that is not in `wa_messages` was sent by someone else. Two candidates exist in the code:

- `LEGACY_WEBHOOK_URL`: in `test` mode the webhook forwards non-listed numbers' raw payload to the legacy system (`webhook.ts:62-64`). If the old agent is still wired to that URL and to the same Z-API instance, it answers by itself, outside this system's log and outside its kill switch.
- Messages with `fromApi: true` are deliberately ignored (`webhook.ts:41`), so API sends by the old agent never appear in `wa_messages`.

Staff typing on the phone is also not in the log, by design.

## 5. Rafaela: "Vejo que você já tem um agendamento… remarcar esse horário ou agendar um novo serviço?"

**PROVEN (code) that the text is not in the repo:** grep for the phrase finds nothing in `src/`, `supabase/`, `scripts/`, `tests/`. It was generated by the model.

Path that produces it: `runClaimed` -> `buildDynamicBlock` (`context.ts:37-72`) puts `CONTEXTO DA CLIENTE ATUAL` (including `next_appointments`) and `AGUARDANDO CONFIRMAÇÃO` in the system block; the persona (`prompt.ts`) says "Chame lookup_client primeiro", whose result also returns the client's upcoming appointments, and nothing forbids volunteering them or offering options ("Ofereça no máximo 3 opções", "Cliente conhecida com profissional habitual: ofereça..."). With a short or unclear inbound ("oi") and a known client with an upcoming appointment, the model fills the gap with an unrequested menu: reschedule or book new. **Which inbound and which trigger exactly (sweep replay of an old message vs a live message): NEEDS PROD DATA** (query 8.5); the sweep replay is the likely trigger because the replayed inbound was old and the answer ignored context.

Fix target: prompt rule "never offer options the client did not request" plus the age/answered gates.

## 6. "Erro do agente"

**PROVEN (code).** The string is a constant in `sweep.ts:30`: when `failed_runs >= 3` and `pending_since` is set, `agent_flag(... 'Erro do agente')`. It says nothing about the cause. The real error is only written with `deps.log('agent_run_failed', {error})` (`agent.ts:34`) = Edge Function console logs, not persisted in the database.

Each failed run (`runAgent` catch, `agent.ts:31-41`) increments `failed_runs`. Retries happen because the sweep (every minute) re-selects any pending conversation with `failed_runs < 3` regardless of age (`sweep.ts:33-37`), and `failed_runs` is reset only on success. A conversation that failed is also retried when mode is switched back to active, which explains runs hours after the original message. **Real error message per case: NEEDS PROD DATA**: Supabase dashboard -> Edge Functions -> `agent-run` logs, filter `agent_run_failed`, 05/10 15:30 onward (query 8.6 lists the conversations to look up).

Fix: persist the real error in `agent_decisions.error_text`, cap retries at 2, never retry messages older than `max_inbound_age_minutes`, never send anything to the client on error.

## 9. Root causes -> fixes (Phase 2)

| Cause | Fix |
|---|---|
| Pending messages survive `off` and are replayed by the sweep with no age limit | Gates 3/4 (live_since, max_inbound_age), quarantine at mode switch, cancel queued on off, sweep + retries pass the same gate |
| fromMe dropped when mode off; no "answered" check | Webhook stores every fromMe; gate 5; send-time re-check; staff pause window |
| Exact-string phone equality | `phone_key` (DDD + last 8 digits), lookup by key, appointments by key |
| Settings read once before a 60 s generation | One send function re-reads settings and thread right before Z-API |
| Anything can call `sendText` | Single outbound function; no other module imports `zapi.sendText` |
| Opaque "Erro do agente", unlimited retries | `agent_decisions.error_text`, max 2 retries, no client-facing error |
| Prompt volunteers options | Prompt rules; context lists only what exists |
| Legacy sender outside the kill switch | Not fixable in code here: confirm `LEGACY_WEBHOOK_URL` is unset/old agent disabled before go-live (GO-LIVE.md) |
